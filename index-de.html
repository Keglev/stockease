Projektvorstellung

Was es ist

Eine zweisprachige Warenwirtschaft für kleine Betriebe: Produkte, Lieferanten, Lagerbewegungen, Rechnungen, Berichte. Java 21 und Spring Boot im Backend, Angular im Frontend, PostgreSQL. Die Anwendung läuft produktiv unter bestandskontrolle.vercel.app; ein Demo-Zugang ohne Passwort ist vorhanden.

Woher es kommt

Die Fachregeln stammen aus meiner Berufserfahrung in der Fertigung: keine Buchung unter Bestand null, Umsatz nur auf gezahlte Rechnungen, Warnung nur für jemals bevorratete Artikel. Jede dieser Regeln ist eine Entscheidung, die ich getroffen und in 42 Architekturentscheidungen begründet habe.

Wie gearbeitet wurde

Drei Rollen, klar getrennt. Ein Chat-Modell entwirft und begutachtet: dort werden Alternativen abgewogen und Spezifikationen geschrieben. Ein in den Editor integrierter Agent setzt diese Spezifikationen um und meldet, was er getan hat und wo er abgewichen ist. Alle fachlichen und architektonischen Entscheidungen treffe ich; ich prüfe jeden Diff und führe jeden Pull Request zusammen. Weicht die Spezifikation vom tatsächlichen Code ab, hält der Agent an, statt den Code zu verbiegen.

Warum das belegbar ist

Jede Änderung ist ein geprüfter Pull Request. Die CI führt die vollständige Testsuite mit Abdeckungsschwellen auf beiden Ebenen aus; eine Regression kann nicht zusammengeführt werden. Ein neuer Test gilt erst als vertrauenswürdig, wenn er aus dem richtigen Grund fehlgeschlagen ist. Angewendete Datenbankmigrationen sind unveränderlich, auch in ihren Kommentaren; ein CI-Schritt erzwingt das, nachdem ein Kommentar-Edit einmal den Produktivstart gebrochen hatte. Die Historie ist öffentlich; jeder Pull Request nennt, was geprüft, was gemessen und was offen gelassen wurde.
